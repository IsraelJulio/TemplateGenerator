### A migração única para dois providers não é armadilha — verificado pelo `reviewer`

O desenho escolhido tem uma migração **só** do Identity para SQLite e PostgreSQL, escrita sem `type:`
nas colunas, com o tipo saindo do mapeamento do provedor em runtime. O risco óbvio é o snapshot
divergir do modelo e quem gerar o projeto levar um `migrations add` espúrio na cara depois.

O `reviewer` apontou (N3) que a afirmação original citava `dotnet ef migrations script`, que **não

### Correção do comando PowerShell

**A causa, medida com `argv` isolado.** Antes de escolher um idioma, o `template-engineer` reproduziu
o defeito num programa que imprime o próprio `argv`, separando o que é do shell do que é do `curl`:

```

   ['-d', '{"title":"Primeiro', 'item"}']      <- DOIS argumentos, JSON truncado
B) literal sem espaco
   ['-d', '{"title":"PrimeiroItem"}']          <- um argumento, por acidente
```

**Cinco idiomas baseados em escape foram testados e todos falham:** corpo em variável (`-d $body` →
aspas comidas), escape duplo, aspas envolventes, `ConvertTo-Json`, e `-replace '"','\"'`. A conclusão
é que nenhuma dose de escape resolve, porque o PowerShell 5.1 decide sozinho se envolve o valor em
aspas e não escapa as internas — qualquer correção por escape seria equilíbrio instável, quebrando no
próximo valor.

**A solução tira o corpo da linha de comando:**

```powershell
'{"title":"Primeiro item"}' | curl.exe -i -X POST http://localhost:5100/items -H "Content-Type: application/json" -H "Authorization: Bearer $TOKEN" --data-binary '@-'
```

Robusto **por construção, não por escape**: o corpo nunca percorre a linha de comando, então nenhuma
regra de citação, de nenhuma versão do shell, pode quebrá-lo.

- A frase de introdução — *"No PowerShell, use `curl.exe` e aspas duplas escapadas"* — foi trocada.
  Ela não era apenas inútil: **ensinava a técnica que não funciona**. Trocá-la era parte da correção.
- A linha de login em PowerShell, criada em B2 e que **funcionava**, foi corrigida também, porque
  "funciona porque não tem espaço" é exatamente o acidente que escondeu o defeito por três tarefas.

## Corrupção silenciosa de acento — achada por medição, corrigida em T06

O `reviewer` levantou `$OutputEncoding` como **nit**, supondo que nada quebraria porque os corpos do
README são ASCII. Medi, e o peso mudou:

```
$ powershell -NoProfile -Command "'{\"title\":\"Primeiro ítem\"}' | & bash.exe -c 'cat > limpo.bin'"
$ od -c limpo.bin
{   "   t   i   t   l   e   "   :   "   P   r   i   m   e   i   r   o       ?   t   e   m   "   }
# UTF-8 correto seria:                                                    303 255
```

`$OutputEncoding.EncodingName` = **US-ASCII**. O `í` vira `?`.

**Por que isto é pior que o defeito do espaço:** o corpo continua sendo JSON válido. O servidor
responde **`201 Created`** e grava `"Primeiro ?tem"`. Não há erro, não há sintoma — só o dado
corrompido. O defeito anterior ao menos gritava `400`.

Três razões para corrigir em T06 em vez de mandar para T11:

1. **É nosso.** A forma antiga quebrava com espaço mas não mexia em encoding. O idioma do pipe foi
   introduzido nesta tarefa; a fragilidade veio junto.
2. **O projeto é em português.** `"Primeiro ítem"`, `"Relatório"`, `"João"` — é o primeiro valor que
   alguém digita ao adaptar o exemplo.
3. **Falha silenciosa é a pior categoria.** Um `400` manda investigar; um `201` com dado corrompido
   não manda ninguém a lugar nenhum.

### A escolha, medida antes de decidir

| | idioma | bytes do outro lado |
|---|---|---|
| hoje | pipe sem fixar nada | `?` (`0x3F`) |
| **(a)** | `$OutputEncoding = [System.Text.UTF8Encoding]::new($false)` antes do pipe | `303 255` ✅ |
| (b) | `Set-Content -Encoding utf8` + `'@arquivo'` | `357 273 277` — acrescenta **BOM** ao corpo |
| (b′) | `[IO.File]::WriteAllText` + `UTF8Encoding($false)` + `'@arquivo'` | `303 255` ✅, mas .NET cru dentro do README |

Escolhida **(a)**, por dois motivos: a forma correta de (b) exige `[IO.File]::WriteAllText` com
`UTF8Encoding($false)` — **.NET cru dentro de um README** — e ela ainda deixa um arquivo temporário
sujando o diretório de quem seguiu o roteiro, mais um comando na sequência. `$OutputEncoding` é, por
definição, a codificação que o PowerShell usa ao escrever no `stdin` de um programa nativo: não é
truque de escape, é a configuração cujo valor padrão causou o defeito.

> **Correção de um erro de fato deste relatório, achado pelo `reviewer` na quarta rodada.** Uma versão
> anterior deste texto descartava (b) também porque o BOM *"não é tolerado pelo leitor JSON do
> ASP.NET Core"*. **Isso é falso**, e ele mediu contra o app gerado: corpo com BOM responde `201` e o
> título é gravado limpo, sem resíduo — o `System.Text.Json` sobre `Stream` pula o BOM UTF-8 desde o
> .NET Core 3.0. A medição de bytes estava certa (`Set-Content -Encoding utf8` no 5.1 escreve
> `357 273 277`); errada estava a **consequência** que lhe atribuí. A decisão sobrevive porque as
> outras duas pernas se sustentam sozinhas, mas o registro tinha de ser corrigido: T07 e T11 leriam
> isto como fato medido, e a próxima pessoa que precisasse escrever um corpo em arquivo descartaria a
> opção pelo motivo errado.

**A mesma medição confirmou, do lado do servidor, a caracterização do defeito.** O `reviewer` não tem
PowerShell, mas pôde medir o que o app faz com os bytes: `201` **tanto para o corpo correto quanto
para o corrompido**, com a corrupção gravada. Eu medi o que sai do shell; ele mediu o que entra no
app. Juntas, as duas metades provam o defeito e a correção ponta a ponta, apesar de nenhum de nós
conseguir cobrir sozinho o caminho inteiro.

**Fraqueza declarada de (a):** é de sessão. Quem abrir outro terminal e copiar só a linha do `curl`
volta ao ASCII. Mitigada pondo a linha no começo de **cada** bloco ```powershell (são três com
Identity), porque cada bloco é uma unidade de copiar-e-colar; a linha é idempotente e o README diz
isso.

> **Armadilha de medição, registrada para quem repetir isto.** A primeira medição do
> `template-engineer` deu mojibake em **todas** as opções, inclusive nas boas — porque o Windows
> PowerShell 5.1 lê um `.ps1` **sem BOM** como ANSI, e o `í` do próprio script de teste já chegava
